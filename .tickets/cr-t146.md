# crane registry serve: clean up abandoned uploads, garbage-collect unused blobs, back off on accept errors

Known gaps in `crane registry serve` (src/registry/), found while building it (cr-u59o notes, 2026-11-09). User asked (2026-11-09) to ticket them. Priority P2 chosen by the agent (tentative): they cost disk and CPU on a long-running registry, not correctness.

**1. Abandoned uploads are never cleaned up**
Code path: POST /v2/<repo>/blobs/uploads/ -> Store::new_upload creates uploads/<id> and puts a running Hasher in the in-memory map (store.rs `hashers()`). Only commit_upload (PUT with ?digest=) or cancel_upload (DELETE) remove them. A client that dies mid-push leaves the file on disk forever and the Hasher in memory until the process exits.
Fix: a janitor that removes uploads/<id> whose file has not changed for longer than a maximum age, and drops its Hasher. Run it once at start (before accepting) and then on a timer thread that shutdown also stops. Age as a flag, e.g. `--upload-ttl 24h` (name and default to confirm with the user; registry:2 has a similar upload-purging setting, check its defaults when building).

**2. Unused blobs are never garbage-collected**
Storage (crane.ts StorageLayout): blobs/sha256/<hex> is shared by all repos; repos/<repo>/_blobs/<hex> is an empty marker meaning the repo holds the blob; repos/<repo>/_manifests/<hex> (+ <hex>.type) and _tags/<tag>. DELETE of a manifest or tag removes only that marker or tag; blob bytes stay forever.
Fix: a separate command `crane registry gc [--disk DIR] [--dry-run]` that takes serve.lock (so it cannot run while a server uses the folder, which avoids racing an in-flight push whose blobs arrive before its manifest). Mark: every repos/*/_manifests/<hex>, parse it (config, layers, subject; index -> child manifests), mark those blobs. Sweep: blobs/sha256 files and repos/*/_blobs markers not marked. Print what is (or would be) removed and bytes freed.
Decisions for the user (proposed default first): (a) offline only (default) vs online with a grace period; (b) keep untagged manifests (default) vs also delete manifests no tag points to; (c) keep blobs a repo holds with no manifest (dropped by sweep in the default).

**3. accept() errors spin**
Code path: src/registry/mod.rs accept_loop: `for stream in listener.incoming() { ...; if let Ok(stream) = stream { spawn_connection(..) } }`. An Err (e.g. EMFILE when out of file descriptors) is ignored and accept is called again at once: 100% CPU until a descriptor frees.
Fix: on Err, sleep with backoff (e.g. 10 ms doubling to 1 s, reset after a success); with -v log the error once per backoff run; stop flag still checked each turn. Test: make accept_loop take the accept call and the sleep as parameters so a unit test feeds Errs and checks the backoff (keeps 100% unit coverage).

**Smaller gaps, same area (record; fix only if cheap)**
- A shutdown during a request-body upload fails that request (the client retries the chunk; data already written stays resumable via Range).
- An upload id is not bound to the repo that started it: any repo can finish it (go's registry behaves the same).

## Acceptance Criteria

- Abandoned uploads older than the max age are removed at start and periodically; their Hasher entries are dropped; unit tests with a fake clock or file mtimes.
- `crane registry gc` removes unreferenced blobs and markers, refuses to run while serve.lock is held, has --dry-run; cross test: after gc, go crane and rust crane still pull every remaining tag with the same digests.
- accept() errors back off instead of spinning; unit test drives the loop with injected errors.
- Decisions (a)-(c) and the flag names recorded on this ticket and in crane.ts (RegistryServeOptions, new gc command).
- Gates stay green: ./test.sh --all, scripts/coverage.sh (100%), scripts/mutants.sh on changed files, scripts/perf.sh.
